# Atlas, metadata and contract

`render_atlas` samples each action with its sampling plan (see [clocks.md](clocks.md)), renders every pose in the eight views of the profile and lays the cells out like the prototype: **rows are views** in heading order (`e, ne, n, nw, w, sw, s, se`), **columns are poses**, the poses of all actions one after another (`idle0 … idle7, run0 … run7`). Frame *i* of the atlas is row *i* div columns, column *i* mod columns; its name is `<pose>.<view>`, e.g. `run3.nw`.

`export_atlas` writes into the output directory:

| File | Content |
|------|---------|
| `atlas.png` | All cells, RGBA, straight alpha, sRGB: each the render with its manual correction on top (see [Manual corrections](#manual-corrections)); without corrections, the render alone. |
| `atlas.json` | Aseprite-style JSON (`json-array`): `frames` with `filename`, `frame`, `rotated: false`, `trimmed: false`, `spriteSourceSize`, `sourceSize`, `duration` (ms); `meta` with `image`, `size`, `frameTags` (one per state, `<action>.<view>` over that action's poses in that view, view by view and in action order: the same names, ranges and order as the tags of `atlas.aseprite`, and the form Aseprite's own JSON export writes) and `slices` (one `foot` slice keyed on frame 0, bounds = the cell, pivot = the profile's ground pivot). |
| `atlas.aseprite` | The same frames as an editable Aseprite file, written directly from the [documented format](https://github.com/aseprite/aseprite/blob/main/docs/ase-file-specs.md) (RGBA, sRGB colour profile): one frame per cell in atlas order with its duration; a base layer `Render` holding the render, whose cel carries the frame's key as user data text (chunk 0x2020 after the cel chunk), and a layer `Manual corrections` above it, empty on a first render and holding the carried corrections after a re-render; one tag per state, `<action>.<view>` over that action's poses in that view; a `foot` slice over the cell with the pivot. Tested by reading it back (with the library's reader and with an independent parser in the tests); not yet opened in Aseprite itself. |
| `pose-contract.json` | `format: "pose-atlas-contract"`, `version: 2`; tool and renderer; `sources` (model path and SHA-256, the profile's values and hash, the render settings and hash; with a palette, `palette` with its path, `sha256` and `colors`); cell, pivot, metres per pixel, cell span; views, columns, pose names; per action the three clocks, loop closure, plan warnings and the render key of each view; `erase_colour`; per frame its name, `key`, action, pose index, view, source time, runtime start, duration, `projected_heading`, `input_sha256` and `render_sha256` (see [Frame keys](#frame-keys)); `files` with the SHA-256 of every other output; with a palette, `palette_report`: `stage`, `alpha_threshold`, `palette_sha256`, `outline_colour` (or null), per (action, view) `renders` and the `total` of `opaque`, `off_palette_before_snap`, `partial_alpha` and `off_palette_output` (see [rendering.md](rendering.md#palette-locked-output)). |
| `corrections-report.json` | Written by `pose-atlas render`: what happened to the manual corrections of the previous `atlas.aseprite` (see [Manual corrections](#manual-corrections)). Not part of the contract. |

Durations are whole milliseconds: the runtime start and end of each pose are rounded and subtracted, so the durations of an action add up to its rounded cycle. A distance cadence without a reference speed has no durations and is refused.

## Validation

`pose-atlas validate <dir>` (`validate_atlas`) ports the rules of the prototype's `check-pose-pipeline.py` that apply here and reports every problem it finds:

- contract format and version; the SHA-256 of every file listed in the contract;
- the contract's cell, pivot, metres per pixel and cell span agree with its embedded profile ("physical framing");
- eight views in heading order; pose names are the actions' poses in column order; every action has a render in every view (state coverage);
- frame count = columns × views in both JSON files; `meta.size` and the PNG size are the atlas size;
- `meta.frameTags` is one tag per state over that state's frames, in the order of the `.aseprite` tags (the prototype had one tag per pose and view, `from` = `to`; engine importers expect the per-state form); exactly one `foot` slice with one key on frame 0, the pivot and full-cell bounds;
- per frame: name, rectangle, untrimmed, unrotated, full source size, zero source offset, duration equal to the contract's and at least 1 ms; `projected_heading` is the unit vector of its screen heading (within 1e-5) and follows from the profile;
- per cell: not blank, and no alpha in the outermost rows and columns (no clipping);
- per frame: `key` is `<action>.<view>@<source time>` as below and unique, and `input_sha256` is the hash of the frame's inputs recomputed from the contract;
- `atlas.aseprite`: cell-sized sprite, one frame per cell with the contract's duration, the two layers, one tag per state over its frames, the `foot` slice with the pivot; every `Render` cel lies inside the cell, carries its frame's key as user data and holds exactly the render the contract hashed (`render_sha256`; the prototype's "Import/export changed raw RGBA pixels" rule, which compared its raw frame files with the cells exported back from Aseprite); the `Manual corrections` layer holds only fully opaque or fully transparent pixels (the first five offenders and the total are reported); and `Render` with the corrections on top, erase-colour pixels cleared, is the `atlas.png` cell. The corrections layer need not be empty;
- the eight views of every pose differ (directions changed), and no action of several poses shows a single image throughout a view (poses changed).
- when the contract names a palette (`sources.palette`): its `sha256` is the hash of its colours and matches the render settings' `palette_sha256`; every opaque pixel of `atlas.png`, which includes the corrections (erased pixels are transparent and so excluded), is a palette colour (or the outline colour, when the render settings have the outline on) and every alpha is 0 or 255 (palette lock). The first five offenders are reported with atlas coordinates, frame and cell coordinates, followed by the totals.

Not ported: the prototype's fixed pose-name and schema lists, its 64/96 px cells and 208 cm span, and its binary-alpha rule for renders without a palette (filtered edges have partial alpha); with a palette, hard alpha is required. Its "every cell differs" rule became the two rules above, because a real animation can repeat a pose; the rig's run does, from the side.

## Frame keys

Every frame has a key that names it independently of its position in the atlas: the action, the view and the pose's source time in seconds, quantised to whole microseconds (rounded to nearest) and written with exactly six decimals: `<action>.<view>@<seconds>`, for example `run.se@0.416667` or `idle.e@0.000000` (negative times get a leading `-`). Adding or removing poses in another action, or changing an action's pose count, keeps the key of every pose whose source time is unchanged (running `run` with 4 instead of 8 poses keeps `run.<view>@0.000000`, `@0.200000`, `@0.400000` and `@0.600000`); differences in the last bits of a computed time disappear in the quantisation. Two frames of one atlas never share a key: `render_atlas` fails before rendering when two poses of an action fall into the same microsecond, naming both frames.

Per frame the contract records `key`; `input_sha256`, SHA-256 over the model file's hash, the profile's hash, the render settings' hash, the renderer, the action, the view and the exact source time (`%.17g`): everything that determines that one pose's render; and `render_sha256`, SHA-256 of the frame's rendered RGBA (cell width × height × 4 bytes, rows top to bottom, straight alpha), before corrections. In `atlas.aseprite` each `Render` cel carries the key as its user data text, so the key stays with the frame when frames are moved in Aseprite.

## Manual corrections

The artist corrects frames by hand on the `Manual corrections` layer of `atlas.aseprite`, with the normal blend mode, in fully opaque or fully transparent pixels. An upper layer cannot erase, so a corrections pixel of exactly the **erase colour** (default `#ff00ff`; `--erase-color` changes it; the contract records it as `erase_colour`) makes that atlas pixel fully transparent. `atlas.png` is `Render` with the corrections on top and erase pixels cleared; frames without a correction are the render alone, so without corrections `atlas.png` is what it was before corrections existed. When the erase colour is also a palette colour (the rig's palette has `#ff00ff`, the colour of its pivot marker), `render` warns: a correction cannot paint that colour.

When `pose-atlas render` finds an `atlas.aseprite` in the output directory whose corrections layer has any pixel with non-zero alpha, it carries the corrections into the new file:

1. **Backup.** Before anything is rendered or written, the file is copied to `atlas.before-<first 12 hex digits of its SHA-256>.aseprite` in the same directory. An existing copy of that name is never overwritten (it has the same content).
2. **Keys.** Each painted frame's key is the user data text of its `Render` cel. For files written before frame keys, the key comes from the frame at the same index of the existing `pose-contract.json` (its `key`, or for older contracts `<action>.<view>@<source_time_s>`), provided that has as many frames. Otherwise `render` stops with a message naming the backup; nothing is overwritten.
3. **Carry.** Each correction is written into the new `atlas.aseprite` at the frame with the same key, at the same position in the cell (clipped to the cell if the cell size changed), as a cel trimmed to its pixels.
4. **Stale.** A carried correction is stale when its frame's new `render_sha256` differs from the render it was painted over (the old contract's `render_sha256` for that key, or for older contracts the hash of the old `Render` cel). A stale corrections cel gets the user data text `stale: render changed` and the user data colour `#ff6600`, which Aseprite shows in the timeline. Stale corrections are still applied to `atlas.png`; check them and clear the mark (or repaint).
5. **Orphaned.** A correction whose key is not in the new atlas (for example a pose that no longer exists after a pose-count change), or whose key an earlier painted frame already had (a duplicated frame), is left out of the new file; it remains in the backup.
6. **Report.** `corrections-report.json` (`format: "pose-atlas-corrections-report"`, `version: 1`) lists `backup` (or null), `discarded`, `carried` and `stale` (each `{key, old_frame, frame}`; the stale ones are also in `carried`) and `orphaned` (`{key, old_frame, reason}`). `render` prints each orphaned key and a summary such as `corrections: 3 carried (0 stale), 1 orphaned; previous file kept as atlas.before-0278bad0c281.aseprite`. Without corrections it prints `corrections: none to carry` and writes a report with empty lists.

`--discard-corrections` skips steps 2 to 5: the backup is still written, the new file has an empty corrections layer. The export stays deterministic: the same inputs and the same corrections give the same bytes. Carried corrections keep their pixels; after a change of `--erase-color`, pixels painted in the old erase colour are ordinary paint. Only the two layers `Render` and `Manual corrections` are read; anything else in the old file is only in the backup.

This supersedes the night-time spike that carried corrections across a re-render with an Aseprite Lua script matched by frame number, which broke as soon as the number or order of frames changed.

## Cache

With a cache directory (`pose-atlas render` uses `<out>/cache` unless given `--cache`), each (action, view) is keyed by SHA-256 over the model file's hash, the profile's hash (all its values, including the filter and supersampling), the render settings' hash (which includes the texture filter, the palette stage, the alpha threshold and the palette's content hash), the renderer description (GL renderer and Mesa version), the action name and its sampled source times, and the view. A stored strip `<key>.png` with that action's poses in that view (and, with a palette, its statistics in `<key>.palette.json`) is reused; otherwise the poses are rendered and the strip is stored. So changing one action's sampling re-renders only that action's eight views; changing the runtime cadence re-renders nothing (it only changes durations); changing the model file, the profile, the settings or the Mesa version re-renders everything. Entries that are missing, unreadable or of the wrong size are rendered again. The contract records each render's key, but not whether it was reused, so a cached and an uncached export are byte-identical.

The model file is hashed as a whole, so editing one animation in the GLB also re-renders the other actions; keying by the data each action actually uses is possible later.
